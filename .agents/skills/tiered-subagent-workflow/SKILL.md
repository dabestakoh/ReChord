# Tiered Subagent Workflow (Project-Wide, Auto-Applied)

The user has pre-authorized this 3-tier model routing across all projects. Apply it automatically whenever `/plan`, multi-file exploration, UI layout changes, implementation, or build/CI verification is needed—do not ask the user to confirm model tiers.

## Core Gates (Mandatory)
1. **Evidence-First Investigation**: Before drafting any plan, gather concrete code evidence (`file:///...#Lstart-Lend`). For bugs/defects, prove the root cause in code; for new features, identify all existing screens, state owners, settings, and callers that will be impacted. Never guess without code evidence.
2. **Strict No-Code-Before-Approval Gate**: **Do NOT** edit code or run modifying commands unless the user explicitly approves the plan or explicitly tells you to proceed/code.
3. **Plain-Language Plan Presentation**: Keep `implementation_plan.md` fully technical (exact file paths, line ranges, diffs, and verification commands) for the coder, **but** present the summary in chat in clear, natural, plain-English IT terms — explaining *what* is happening, *why*, *which screens/settings/libraries* are affected, and *what changes for the user* — without assuming Java, Kotlin, or Jetpack Compose knowledge.
4. **Model / Reasoning Recommendation in Every Plan**: At the end of every `/plan` response (right at the approval gate), include a 1-line recommendation on whether the user's everyday worker model (e.g. **Hydrogen** / `inherit`) is sufficient to implement the plan, or whether switching to a higher-reasoning model (e.g. **Neon** / `pro`) is recommended due to complex multi-file state, animation, or audio-pipeline interactions.
5. **Visibility Rule (1-Line Badge)**: Include a brief 1-line badge in your response showing active tiers (e.g., `Workflow: tiered-subagent-workflow [flash scout → pro/inherit plan → pro UI review → flash_lite verify]`, or `Workflow: tiered-subagent-workflow [direct edit — trivial slice]`).

## Tier Roles

| Tier (`Model`) | Subagent Type | Responsibilities | Guardrails |
| :--- | :--- | :--- | :--- |
| **`flash_lite`** | `runner-watcher` (write/cmd) or `research` (read-only) | Runs builds/tests (`./gradlew`, `npm`, `pytest`, etc.) — **including all retries, rate-limit fallbacks, and post-fix re-runs** — watches CI (`gh run watch`), checks `git status`, performs clean merges, and does simple file discovery. Returns a compact `< 200-token` pass/fail or status summary. | **Never** resolve non-trivial compiler errors or merge conflicts on its own — report exact error/conflict lines back to `pro` / `inherit`. **Never** pull Gradle/build retries back into the main lead session: if `flash_lite` hits network rate limits (e.g. Maven Central `HTTP 429`), forward the fallback command (such as `--offline` or a temporary Google Maven mirror init script `-I /tmp/gcs_mirror.gradle`, cleaned up afterward) directly to the warm `flash_lite` runner via `send_message`. |

| **`pro`** | `ui-layout-reviewer` (read-only) | **UI Layout Reviewer (UI tasks only):** **Always** audits proposed or edited UI/layout code for **Portrait and Landscape**, **DAPs (Digital Audio Players)**, **Car Head-Units** (wide/short aspect ratios and specific resolutions, e.g., `560–720×360dp`, `640×360dp`, `853×480dp`, `1280×720dp`), and tablets; checks safe-area/cutout insets across root & dialog/sheet windows, clipping, overlapping hitboxes, text overflow, and project-specific rules (such as `rechord-compose-perf-audit`, Local vs. Online Library non-conflict, and ReChord Settings compatibility). | Only spawn when UI/layout files are involved. Always consider **Portrait, Landscape, DAPs, and Car Head-Units** on every UI change. | Skip spawning subagents for trivial 1–2 file edits where line ranges are already known. ## Automatic Execution Flow
1. **Investigate First (`flash`)**: Gather code evidence (`file:///...#Lstart-Lend`) proving the bug/defect or mapping existing features/callers impacted by a new feature.
2. **Plan (`pro` / `inherit`)**: Read only the targeted line slices and write the technical `implementation_plan.md` (explicitly covering Portrait + Landscape, DAPs, Car Head-Units, Local vs. Online Library, and Settings impacts when applicable).
3. **UI Layout Review (`pro`, UI tasks only)**: When UI/layout code is planned or modified, run a read-only `pro` UI Layout Reviewer on the affected UI slices.
4. **Approval Gate + Plain Summary + Model Recommendation**: Present the plan in plain, natural IT-friendly language (no Java/Kotlin/Compose assumptions) with a 1-line **Model Recommendation** (everyday worker like **Hydrogen** vs. higher-reasoning like **Neon**) and wait for explicit approval to proceed/code.
5. **Implement (`inherit` / `pro`)**: Apply the approved changes cleanly.
6. **Verify & Watch (`flash_lite`)**: Spawn or `send_message` a `flash_lite` runner subagent to execute build/test commands, clean merges, or `gh run watch`, reporting only pass/fail and exact failure lines. **Keep all retries on `flash_lite`**: if a build hits Maven Central `HTTP 429` or another transient network/cache snag, or after the lead agent fixes a compile/test error, always forward the retry (e.g. `--offline` or temporary Google Maven mirror `-I /tmp/gcs_mirror.gradle`) directly to the warm `flash_lite` runner via `send_message` rather than running Gradle in the main session.
