# ReChord agent instructions

Read the [ReChord engineering standards](docs/RECHORD-STANDARDS.md) before planning or editing. It is the canonical guide for coding, UI, playback, add-ons, and delivery. When assessing or syncing upstream BitChord updates, also read the [ReChord upstream sync policy](docs/UPSTREAM-SYNC-POLICY.md) to avoid pulling intentionally omitted features.

- Keep planning and investigation read-only until the user approves implementation. Keep `implementation_plan.md` technical for the coder, and write **all** chat responses (plans, progress updates, summaries, and completion reports) in clear, natural, non-technical plain-English language—explaining what changed, why, which screens or settings are affected, and how it behaves for the user—without exposing internal class/function/parameter names, Kotlin/Compose code syntax, or Gradle task jargon.
- Automatically load and follow [tiered-subagent-workflow](.agents/skills/tiered-subagent-workflow/SKILL.md) on every `/plan`, investigation, UI review, build, or release task (pre-authorizing `flash_lite`, `flash`, `pro`, and `inherit` tier routing without manual prompting).
- Treat Portrait and Landscape — including cutout/gesture phones (rotated both ways), 3-button-nav phones, DAPs (`560–720 × 360 dp`), Car Head-Units (`640 × 360 dp`, `800 × 480 dp`, `853 × 480 dp`, `1024 × 600 dp`, `1280 × 720 dp`), and Tablets — as equal first-class targets in every UI, design, logic, and animation change. Before presenting any `/plan` or pushing a Preview APK, proactively audit: (1) horizontal safe-area insets (`navigationBars ∪ displayCutout`) across both the main Activity root and every separate `ModalBottomSheet` / `Dialog` window so no control ever crosses system bars or punch-holes in landscape; (2) full-width scrims and tap guards so they never dim or swallow touches on side rails (such as the A–Z index); (3) Portrait non-regression when fixing Landscape (and vice versa); (4) synchronous Frame-1 state/scroll updates (`requestScrollToItem`, state holders) vs. delayed `LaunchedEffect` / `withFrameNanos` flashes, touch hitboxes, row text boundaries, and per-frame GPU/shader allocations; and (5) **every toggleable Setting** (`reduceDynamicBlur` / Reduce Liquid Glass, `reduceAnimation` / Reduce Motion, Light/Dark theme, Autoplay, Lyrics/Stats/Volume visibility, and Home section toggles) so every layout adapts cleanly when any option is turned off or on without prompting.
- Work on the current or explicitly named branch. Ask before creating or switching branches. Merge and run release workflows only as authorized.
- Preserve existing app data, package identities, signing keys, audio behavior, and compatibility with query-only add-ons. Verify affected entry points and module builds (`:sharedUi:jvmTest`, `:sharedUi:compileDebugKotlinAndroid`, `:app:compileDevDebugKotlin`, `:tv:compileDevDebugKotlin` when shared code or `BuildConfig` fields affect TV, and `:app:testDevDebugUnitTest --tests "com.music.bitchord.LocaleStringsTest"` when adding/changing string keys) before reporting completion. Always upload Preview APKs directly as a single unzipped `.apk` (`actions/upload-artifact@v7` with `archive: false`), never wrapped in a `.zip`.
- Follow the approved scope and report in plain, non-technical English what was verified (e.g., unit tests and phone/TV builds passed). Write release notes (`docs/releases/v<version>.md`) in clear, non-technical, user-friendly language (noting the upstream BitChord base version when applicable), and when authorized to release on `main`, monitor all triggered release workflows to completion and fix any build/test issues. For documentation-only changes, skip push-triggered builds (`[skip ci]`) unless requested.
